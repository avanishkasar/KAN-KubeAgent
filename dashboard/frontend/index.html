What this page shows

KAN-KubeAgent watches a real training job and decides, every couple of epochs, whether to let it continue, lower its learning rate, or stop it. A small Kolmogorov-Arnold Network (KAN) makes that decision, and it can be written out as a formula. This page explains every number and chart in the other tabs.

Each chart and tile has a what is this? link that brings you to the matching section here. A job's progress is judged on validation loss: the model's error on images it never trains on. Lower is better. Training loss is shown next to it for comparison.

The five features

The gate sees only these five numbers, each between 0 and 1, computed from the validation-loss history so far.

  • Loss plateau: 0 while the loss is still dropping quickly, 1 when it has stopped moving over the last five epochs.
  • Gradient trend: the recent average gradient size relative to the largest seen in this run. Near 1 means the model is still being pushed hard.
  • LR-decay benefit: how often the loss goes up and down from one epoch to the next. A jittery curve suggests a smaller learning rate would help.
  • Budget remaining: the unused share of the planned epochs. This is an epoch count, not measured GPU time.
  • Since improvement: epochs since the best validation loss, divided by 30.

Status, epoch, validation accuracy, run number

  • Status: Starting while the process loads, Running while it trains, Completed when it finishes all epochs, Stopped when you stop it, the gate stops it, or it crashes.
  • Epoch: how many full passes over the training images have finished. The small text is the learning rate in use now.
  • Val accuracy: the share of 2,000 held-out test images classified correctly after the latest epoch. The small text is the best validation loss so far.
  • Auto run #: with Auto-continuous on, each finished run is followed by a fresh one. The number counts runs, and the small text counts epochs trained in this session. Each run starts from new random weights.

See it on the Live tab.

CPU, memory, GPU

These describe the whole machine, not only the training process. A browser, an editor or a video call all add to them.

  • CPU: system-wide utilisation across all cores.
  • Memory: RAM in use across the machine.
  • GPU: utilisation of the NVIDIA GPU as reported by nvidia-smi. If it says "No GPU detected", nvidia-smi was not found. Intel and AMD GPUs are not read, and training can only use an NVIDIA GPU, and only if the CUDA build of PyTorch is installed. Otherwise training runs on the CPU and the GPU stays near zero.

Latest decision

The most recent verdict from the gate: Continue (score under 40), Adjust LR (40 to 75, the learning rate is halved) or Early stop (75 or more, the process is terminated). The small text counts every decision of each kind made in the session.

Agent pipeline

Five steps run in order each time the agents are invoked. A step lights up when it actually finishes.

  • Metrics Watcher (code): reads the job's loss history and learning rate.
  • Loss-Curve Analyst and Cost (code): turns the history into the five features.
  • Supervisor (LLM): proposes an action with a reason. It is a suggestion only.
  • KAN Gate: scores the features. Its decision is the one that is executed. If it disagrees with the Supervisor the page says "KAN overrode".
  • Executor (code): does nothing, writes a new learning rate to a file the training process reads each epoch, or stops the process.

Because training keeps running while the agents work, a decision takes effect at the next epoch boundary.

Loss and gate decisions

The horizontal axis is epochs of the current run. The blue line is validation loss, the orange line is training loss.

  • Training loss usually keeps falling. Validation loss falls, flattens, and may rise again. Rising validation loss with falling training loss means the model is memorising the training images (overfitting). The best point to stop is the lowest part of the validation line.
  • Each dot is one gate decision, placed on the validation line at the epoch it looked at: green continue, amber adjust learning rate, red stop. Hover a dot for its score.
  • Hover the chart for exact values at any epoch.

The chart restarts at every new run in Auto-continuous mode.

Inside the KAN, latest decision (small)

A compact picture of the latest decision. Five nodes on the left are the features, the middle column is the hidden layer, the right node is the stop score. Each line is a learned function. Line thickness is how much that function matters over typical inputs; a blue line pushes the score up for this input and a red line pushes it down. A dashed middle node was pruned during training and carries nothing. The bars underneath show how much each feature added to or took from the score. The full version is on the KAN Network tab.

Real-time hardware load

Three lines (CPU blue, memory orange, GPU green), one sample about every two seconds, covering the last five minutes or so: CPU, memory and GPU as above. A hump when a run starts is normal: loading PyTorch, reading the dataset and starting data workers. Utilisation then holds near the level the selected mode allows, and falls when the run ends. A drop at the end of the chart usually means the run finished, not that the system is throttling.

Process and decision log

A running record: the hardware check at launch, every line the training process prints, each agent invocation, each gate verdict with its largest contributing feature, and every learning-rate change. Nothing in it is scripted.

Decision audit log

One row per decision, newest first. Epoch is the epoch it looked at. Score is the gate's 0 to 100 stop score. Top driver is the feature that moved the score most (occlusion contribution, see the waterfall section). Outcome is what was done: NO_OP, LR_ADJUSTED or EARLY_STOPPED. LLM proposal is what the Supervisor suggested. Formula is the exact function that produced the score.

The network drawing

This is the real gate. The left column holds the five features and the numbers fed in. Each line is one edge, and the small box on it plots the function that edge applies to its input (shown for the four most important edges; all are in the edge section below). The middle column is three hidden nodes that add their incoming edges together. The right node is the stop score. Move a slider on the left, or load a past decision, and the numbers, colours and score update from the real gate.

  • Thickness: how much the edge's output varies across typical inputs.
  • Blue line: the edge raises the score for the current input. Red: it lowers it.
  • Dashed circle: a pruned node.

Verdict and bands

The big number is the stop score for the current inputs. Below 40 the gate says continue, from 40 to 75 adjust the learning rate, from 75 up stop. The marker shows where the score sits on that scale. The bands are fixed cut-offs and are the same for every run.

How the score was built

The first bar is the baseline: the gate's output when every feature is zero. Each following bar is one feature's contribution: the output minus the output with that single feature set to zero. The last bar is the score. Blue bars raise it, red bars lower it.

The contributions add up exactly to the score only when the network is additive. The note under the chart says whether that holds for the gate in use. When it does not, the bars are estimates, but the formula next to it is still exact.

The formula the gate executes

After training, every edge is replaced by a closed-form function (a line or a sine). Chaining them gives this expression. It is not a summary of the model: evaluating it gives the same score as the network, to within a few thousandths of a score point. That is what makes each decision auditable.

Learned edge functions

One small plot per active edge, ordered by importance. The horizontal axis is the input to that edge, the vertical axis is its output, and the line below gives the formula. The white dot marks the current input. A straight line means the gate uses that input proportionally; a wave means it responds non-linearly.

Benchmark overview

These results are not live. They come from 36 complete training runs recorded without any intervention (6 learning rates, 2 batch sizes, 3 seeds, 40 epochs each). Every stopping method was then replayed on those same curves. The gates were tested on runs they never saw: each seed's runs were held out in turn.

The four tiles at the top report the KAN gate trained with hindsight labels: share of compute saved, mean regret, premature-stop rate, and faithfulness (the largest difference, in score points, between the displayed formula and the network's actual output).

Compute saved, regret, premature stops

  • Compute saved: the share of the 40-epoch budget not used because a run was stopped.
  • Regret: how much worse the best validation loss reached by the stopping point is than the best the full run ever reached, as a percentage. Zero means nothing was lost.
  • P90 regret: the regret that 90 percent of runs stay below.
  • Premature: the share of runs with regret above 2 percent, meaning they were stopped while still improving.

A good method saves a lot of compute with little regret. Saving compute alone is easy: stop everything at epoch 1.

Compute saved vs regret

Each dot is one method. Right means more compute saved, lower means less regret, so the best methods sit bottom right. The regret axis is stretched at the low end so small differences can be seen. The bars on the paper version show variation across the three gate training seeds. The hindsight oracle is a reference that knows the future and cannot be used in practice.

Per-run results table

The same measurements as numbers, with the method trained by us highlighted. "Patience-N" stops after N epochs without improvement. The median rule stops a run that is worse than its peers, so its per-run regret is large by design. "teacher labels" means the gate was trained to copy a hand-written rule instead of learning from outcomes. The values after the plus-minus sign are the spread over three gate training seeds.

Example held-out runs

Validation loss for individual runs, with a dashed vertical line where each method stopped it. A line at the right edge means the method let the run finish. Lines far to the left of the loss minimum stop too early; lines far to the right of it waste epochs.

Training modes and system load

  • Background: the process gets low OS priority, a quarter of the CPU cores, one thread and a short pause after each batch. It trains slowly and stays out of the way.
  • Normal: default priority and a few data-loading workers.
  • Turbo: more workers and mixed precision for speed. It uses as much of the machine as it can.

Train on chooses the device: Auto uses the NVIDIA GPU when PyTorch can see one, a numbered entry pins the run to that GPU, and CPU only forces the processor. The notice under the control deck appears when a GPU exists but PyTorch cannot use it. Running start.ps1 or start.sh again installs the matching CUDA build of PyTorch.

The CPU in this tool is the training process. If the GPU is busy while the NVIDIA GPU reads zero, something else on the machine is using it: the browser drawing a page, a video, another application.

Mock / synthetic mode

No real process runs here — a synthetic loss curve (with an optional injected plateau) is generated instantly and scored by the same real KAN gate. Useful for fast iteration and reproducing specific edge cases without waiting on real training. See research/proposal/methodology_draft.md Section 6.2.
